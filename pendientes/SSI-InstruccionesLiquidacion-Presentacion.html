01 · Introducción

¿Qué es una SSI (Instrucción de Liquidación)?

Una Settlement Instruction es una instrucción permanente que define cómo entregar cash o securities a una contraparte y mediante qué método de liquidación.

Liquidación según SDIs válidas

Cuando un trade llega al BO, el sistema liquida según las SDIs válidas que posea para la combinación Contraparte + Divisa + Producto + Fechas. No requiere intervención manual.

Maestro en RDR

RDR es el sistema maestro de instrucciones de liquidación de BBVA CIB. En ellas se encuentra toda la información para la liquidación: contrapartida-divisa-producto-fechas. RDR suministra estas instrucciones al BO.

Datos clave de una SSI: Contrapartidas/Participantes (quién liquida, beneficiario, corresponsal/custodio, intermediario), Producto, Intervalos de fecha (vigencia), STP (asignación automática Y/N), Branch (geografía), Divisa.

01 · Conceptos

Conceptos Básicos

Elementos fundamentales para comprender las instrucciones de liquidación.

Liquidación

Proceso de cálculo final para cerrar o saldar una operación. Es el momento del intercambio definitivo entre el dinero y el activo.

Flujo de una Operación

Camino secuencial y cronológico que recorre una operación desde que se pacta hasta que se procesa, se paga definitivamente y se archiva.

Sentido de Liquidación

Lo que para uno es un gasto, para el otro es un ingreso. El sentido siempre se define desde la entidad que origina la instrucción.

MIS (OWNENT)

Instrucción de liquidación de la PO (Processing Org). Es la instrucción propia de la entidad (SPAIN, MEXICO, BSI…).

SUS (CPARTY)

Instrucción de liquidación de la contrapartida. La SDI que corresponde a la entidad con la que se opera.

Liquidación a Terceros

Cuando la dueña de la instrucción y el beneficiario no coinciden. La contrapartida que opera y la que liquida no es la misma.

Regla fundamental: Si una operación liquida, debe existir instrucción tanto de la PO (MIS) como de la contraparte (SUS). Además, ambas deben tener el mismo tipo de método de liquidación.

01 · Características

Características Principales

Propiedades clave de una SSI que determinan su comportamiento y aplicación.

🔑

Clave funcional

(Counterparty, Currency, Product, Asset Type) determina la SSI aplicable

📐

Jerarquía de aplicación

SSI específica (divisa+producto) > SSI general (divisa) > SSI por defecto

📅

Vigencia temporal

START_TMS / END_TMS permiten planificar altas/bajas futuras sin intervención manual

⚡

STP (Straight-Through)

STP=Y asigna automáticamente la SDI a las operaciones (si no hay colisión de prioridad)

🔒

Trazabilidad regulatoria

BCE/EMIR exigen conservar la SSI original. Cada cambio queda auditado

🏦

Multi-país

Reglas por branch: México (SPEI/SPID), España (A1), Colombia (C1)

02 · Tipos de Pago

Tipos de SSI según Instrucción

El campo Instruction Type discrimina dos grandes familias, cada una con su propia cadena de participantes y reglas de enrutamiento.

💰 CASH (Pagos)

Instrucciones para liquidación de efectivo — transferencias de fondos entre cuentas bancarias.

  • • Genera mensajes SWIFT MT103 / MT202
  • • Requiere cuenta bancaria del beneficiario (IBAN/CLABE)
  • • Cadena: Ordenante → Banco Corresponsal → Banco Beneficiario
  • • Relevante Colombia: Client Cash obligatorio en C1
  • • Código ABA para enrutamiento USA

📄 SECURITY (Valores)

Instrucciones para liquidación de valores — transferencia de títulos entre cuentas de custodia.

  • • Genera mensajes SWIFT MT540/541/542/543
  • • Requiere cuenta de custodia/valores (safekeep account)
  • • Cadena: Beneficiario → Clearing → Custodio → Depositario
  • • Security Account por sucursal
  • • Sujeta a penalización CSDR por settlement fails

Impacto del tipo: El Instruction Type condiciona las sub-secciones visibles en pantalla, los lookups disponibles y los participantes obligatorios de la cadena de liquidación.

02 · Métodos

Métodos de Liquidación

El campo Settlement Method Type define el mecanismo por el cual se efectúa la liquidación y qué participantes son obligatorios.

Método Nombre Descripción Tipo
CLS Continuous Linked Settlement Liquidación simultánea multi-divisa para FX (17 divisas principales). Cash/FX
EBA / TARGET2 Euro Banking Association Métodos exclusivos para divisa EUR. Cash
CONTABLE/GDI Account Según cuenta beneficiario: si primeros 4 dígitos = 0182 y posiciones 11-13 ≠ 008/220/225/230 → GDI, sino → CONTABLE. Cash
SWIFT SWIFT Método para divisa distinta a EUR vía red SWIFT. Cash

Nota: Existen más métodos de liquidación (DVP, RVP, FOP, CORRESP, CLEARING, CUSTODY…) aplicables principalmente a Securities. Los mostrados aquí son los más relevantes para la operativa Cash.

Regla MIS/SUS: Para cada operación, la SDI MIS y la SDI SUS deben tener el mismo tipo de método de liquidación. Si no coinciden, Calypso no puede asignar correctamente.

04 · Gestión

Procesos de Interfaz de Usuario

Operaciones principales de gestión de SSIs desde Workstation.

🔍

Búsqueda

Por contraparte, divisa, producto, método, estado. Filtro ACTIVE por defecto.

➕

Alta

Creación. Se selecciona contraparte (no editable después), método, side, tipo. Submit genera ID.

✏️

Modificación

Una vez dada de alta, casi todos los campos quedan como no editables. Solo se pueden editar campos limitados.

🔄

Inactivar + Nuevo

Transacción atómica: inactiva la SSI actual y crea una nueva vinculada. Para cambios estructurales.

📋

Copiar

Clona SSI existente con nuevo ID. Todos los campos editables. Útil para variantes por divisa.

🔀

Reasignar

Variante para reasignar a otra contraparte. Inactiva la vieja, crea nueva apuntando a otra entity.

Anexo · Objetivos

Objetivos de la Migración: Instrucciones de Liquidación

Una vez las operaciones migran al nuevo BO a través de la caída de operaciones, deben seguir su curso de vida: liquidar, confirmar, notificar, reportar.

¿Cuándo es necesaria una SDI?

Es totalmente necesario que todas las operaciones queden asignadas a una instrucción de liquidación siempre que al menos uno de sus flujos sea pasado.

  • • Una migración se realiza en un momento D concreto
  • • Una operación puede tener algún flujo realizado pero no todos
  • • Si todos los flujos son posteriores al GoLive → la necesidad se debe revisar

Regla fundamental

Para cada operación (combinación de contrapartida + producto + divisa + fecha) debe existir una SDI en RDR y el BO.

  • • Debe existir instrucción de la PO (MIS)
  • • Debe existir instrucción de la contraparte (SUS)
  • • MIS y SUS con mismo método de liquidación

⚠️ Importante: El análisis debe actualizarse periódicamente. Las migraciones se dilatan en el tiempo: instrucciones inicialmente válidas pueden acabar inactivándose, e instrucciones pendientes de alta puede que finalmente no sean necesarias.

Anexo · Análisis

Análisis de Instrucciones de Liquidación

RDR como maestro de datos estáticos debe identificar el estado de las SDIs para la operativa viva que migra.

Papel de RDR en la migración

  • 📌 Diccionario entre aplicativos (caída de operaciones)
  • 📌 Maestro que suministra al BO las instrucciones de liquidación
  • 📌 Facilitador de datos fijos para que la operación se liquide y confirme

Análisis requerido

  • ✅ Identificar operaciones que ya cuentan con SDI válida en RDR y BO
  • ⚠️ Identificar operaciones que no cuentan con SDI válida
  • 🔧 Para las que no tienen SDI → revisar cuál dar de alta

⚠️ Actualización continua

El análisis debe actualizarse periódicamente: antes de cada simulacro y posterior a él. Lo mismo para el GoLive. Las migraciones se dilatan y el estado de las instrucciones cambia con el tiempo.

Recuerda: Del mismo modo que la operativa viva, las instrucciones de liquidación tienen que revisarse cíclicamente. Instrucciones válidas hoy pueden inactivarse mañana.

Anexo · Alta de SDIs

Proceso de Alta de SDIs

Cuando se detecta la inexistencia de una SDI para una operación, se debe dar de alta mediante la plantilla de carga masiva de RDR.

Plantilla de carga

En RDR existe una plantilla de carga de SDIs para cargas masivas.

  • • La responsabilidad de informar la plantilla es del usuario y/o el BO
  • • Desde RDR se ofrece soporte para ayudar a informarla
  • • RDR prueba la carga y publicación al BO

Responsabilidades claras

Es muy importante no responsabilizarse de la tarea de informar la plantilla:

  • ❌ Desde RDR IT no se tiene el conocimiento ni poder de decisión sobre el tipo de SDI
  • ✅ Es tema de negocio
  • ✅ El usuario debe estar siempre presente en cada decisión de publicación

Anexo · Durante Simulacro

Flujo de Trabajo: Durante los Simulacros

Acciones que RDR debe ejecutar durante el simulacro para asegurar cobertura completa de SDIs.

Tareas durante el simulacro

  • ✅ Asegurar que el eepp donde se realiza está correctamente levantado
  • ✅ Verificar que el handler está funcionando
  • ⚡ Si surge operación nueva → dar de alta SDI necesaria
  • 📝 Apuntar todas las SDIs dadas de alta durante el simulacro
  • 📝 Apuntar todas las publicaciones realizadas

⚠️ Regla de Oro

"De nada sirve solucionar un error si no queda inventariado"

Cada SDI dada de alta o publicada durante el simulacro debe quedar registrada inmediatamente. Si no se apunta en el momento, se pierde.

Post-simulacro inmediato (lunes): Enviar correo con resumen de acciones realizadas de SDIs:

  • 📧 Altas → Deben ser informadas en la plantilla por el BO
  • 📧 Publicaciones → Deben quedar apuntadas en el inventario de tareas de RDR

Anexo · Post-Simulacro

Flujo de Trabajo: Después de un Simulacro

Análisis de errores de asignación y plan de acción iterativo hasta el GoLive.

Evolución esperada

Dependiendo del momento y tipo de simulacro puede haber más o menos errores:

  • 🔴 Primer simulacro: Normal que salgan más errores. Suele ser técnico: detectar gaps
  • 🟡 Simulacros sucesivos: Deben ir limitándose los errores, depurando la plantilla
  • 🟢 GoLive: Foto limpia de acciones de carga

Acciones post-simulacro

  • 1. BO saca listado de errores de asignación
  • 2. BO analiza el tipo de error
  • 3. RDR apoya: ¿existe en RDR? → Publicar (inventariando)
  • 4. ¿No existe? → BO informa la plantilla para dar de alta
  • 5. Usuario siempre consultado → la SDI X correcta para subsanar

Anexo · Calypso

Funcionamiento de BO Calypso — Errores de Asignación

Para agilizar el análisis, es fundamental entender cómo Calypso asigna las instrucciones y qué errores pueden producirse.

Requisitos de asignación

  • 📌 Para cada operación (contrapartida-divisa-producto-fechas) se necesita SDI SUS + SDI MIS
  • 📌 MIS y SUS deben tener mismo tipo de método
  • 📌 STP = Y permite asignación automática (si no hay colisión de prioridad)

Tipos de errores de asignación

  • ❌ Más de una SDI con misma prioridad válida → no puede elegir automáticamente
  • ❌ No existe SDI válida, o la que existe no tiene STP o es a terceros
  • ❌ No hay SDI MIS para la operación
⚠️

Colisión de prioridad

Varias SDIs válidas con misma prioridad. Calypso no sabe cuál elegir.

🚫

Sin SDI válida / sin STP

No existe instrucción o la que existe no tiene flag automático.

🏢

Sin MIS (OWNENT)

Falta la instrucción de la Processing Org para la operación.

Acción: Tras cada simulacro, BO saca el listado de errores → BO analiza el tipo de error → RDR apoya: si la SDI existe en RDR hay que publicar (inventariándolo), si no existe se debe dar de alta y BO informa la plantilla.

Resumen

Claves de las Instrucciones de Liquidación

1

RDR es el sistema maestro de instrucciones de liquidación. Suministra al BO las SDIs necesarias para que las operaciones se liquiden correctamente.

2

Cada operación necesita SDI MIS + SDI SUS con el mismo método de liquidación para que Calypso la asigne automáticamente.

3

La preparación para migración/simulacro requiere análisis cíclico: extraer, identificar faltantes, cargar y publicar.

4

"De nada sirve solucionar un error si no queda inventariado" — Todo cambio aplicado debe registrarse inmediatamente en el inventario para producción.

5

La responsabilidad de decidir qué SDI dar de alta es de negocio/BO. RDR da soporte técnico: carga, publicación y verificación ACK/NACK.
